# 7. NO ROLLING LIVE PREVIEW: ARCHITECTURAL REQUIREMENTS

The absence of the rolling preview must be enforced at the application architecture level.

Do not implement the preview and hide it with CSS.

Do not create a hidden list of generated values.

Do not maintain an unnecessary array of recent entries solely for display.

Do not repeatedly format individual generated values for display.

Do not create one UI update for every generated value.

Do not introduce a scrolling text area.

Do not implement automatic scrolling.

Do not implement a preview refresh timer.

Do not implement preview-only state management.

Do not keep a preview buffer that grows with the number of generated entries.

### Required processing architecture

Use a separation between:

1. Generation logic.
2. Progress and statistics reporting.
3. Data persistence.
4. User interface.

The generation engine should process values independently of the rendering layer.

The UI should receive aggregated progress information at a controlled rate.

For example, progress updates could be emitted periodically or at completed batch boundaries, depending on the original application's needs.

The update interval must not interfere with the generation engine or change the meaning of the reported statistics.

The exact interval should be chosen through performance testing rather than assumed to be optimal.

### Generated-data handling

Generated values must be passed to storage or output processing through the appropriate existing mechanism.

Do not retain every generated value in RAM unless the application's actual requirements necessitate it.

If generated values must be saved, process them through bounded batches.

Do not lose values at batch boundaries.

Do not introduce duplicate values when flushing batches.

Do not confuse statistics with stored generation records.

The removal of the preview must not prevent the application from generating, saving, exporting, or recovering its data.
